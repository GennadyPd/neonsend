## 1. Что это за проект

**NeonSend** — приложение для Windows, которое превращает компьютер в локальный «обменник файлов»:
запускаешь один `.exe`, в окне появляется QR-код и адрес вида `http://192.168.1.25:8765`,
любое устройство в той же Wi-Fi/LAN-сети открывает страницу в браузере и передаёт файлы
или текст без установки приложений, аккаунтов и интернета.

Проект вырос из практической задачи пользователя: перенести файлы с другого компьютера
на этот ПК. Первая версия была на Python (`C:\Temp\opencode\transfer.py`) и работала,
но имела проблемы (см. §11), поэтому было решено переписать всё на Rust в виде
одного переносимого `.exe` с современным тёмным интерфейсом.

### Ключевые требования пользователя (сводка, подтверждённые перепиской)

| Требование | Статус |
|---|---|
| Один `.exe`, без установки, переносится на флешке | реализовано (release ~3.7 МБ, конфиги в `%APPDATA%`) |

| Получатель подтверждает приём на своём экране | реализовано |

## 2. Технологический стек (фактический, из Cargo.toml/Cargo.lock)

- **Язык:** Rust 1.100.0, edition 2021, toolchain `stable-x86_64-pc-windows-gnu`.
- **Компилятор C:** MinGW-w64 GCC 16.2.0 (MSVC/VS Build Tools на машине отсутствуют).
- **GUI:** `eframe`/`egui` 0.37 — нативное окно, без WebView2 и без внешних зависимостей.
- **HTTP-сервер:** `axum` 0.7.9 на `tokio` 1.54.1 (multi-thread runtime), `hyper` 1.12.0.
- **Сериализация:** `serde` 1.0.229 + `serde_json` 1.0.154 (JSON, без бинарных форматов).
- **Время:** `chrono` 0.4.45 (`clock`, локальное время в журнале).
- **QR:** `qrcode` 0.14.1 (без `default-features`, рендер в текстуру egui вручную).
- **Диалог выбора папки:** `rfd` 0.14.1.
- **Сетевые интерфейсы:** `if-addrs` 0.15.0 (выбор LAN-IP с обходом VPN-адаптеров).
- **Потоки/утилиты:** `futures-util` 0.3.34.
- **Тесты:** встроенный `cargo test` (`#[tokio::test]`), 5 юнит-тестов в `src/server.rs`.
- **Фронтенд:** один статический файл `src/page.html` — ванильный JS + CSS, без фреймворков,
  вкомпилирован в бинарник через `include_str!`. Никаких CDN и внешних ресурсов.
- **Сборка:** `cargo build` / `cargo build --release`; release-профиль: `opt-level="s"`, `lto`,
  `codegen-units=1`, `panic=abort`, `strip`.
- **Хранение:** файлы на диске + два JSON-файла настроек. Базы данных нет.

Всего 473 пакета в `Cargo.lock`.

## 4. Архитектура в одном экране

```
┌─────────────────────────────┐        HTTP (JSON + raw body)        ┌──────────────────────┐
│  neonsend.exe (Windows)     │ ◄──────────────────────────────────► │ Браузер на телефоне  │
│                             │                                      │  page.html (4 экрана)│
│  egui-окно (main.rs)        │        SSE /api/events               │                      │
│   • QR, адрес, папка        │ ◄──── события состояния комнаты ──── │  EventSource         │
│   • подтверждение для ПК    │                                      │                      │
│   • список устройств        │                                      └──────────────────────┘
│                             │                                                ▲
│  axum-сервер (server.rs)    │                                                │
│   • Shared: устройства,     │        HTTP                            другой браузер
│     комнаты, журнал         │ ◄──────────────────────────────────────────────┘
│   • файлы: папка приёма /   │
│     Temp(от-кому-комната)   │
└─────────────────────────────┘
```

- **Устройство = токен в браузере** (`localStorage['neon-token']`, ключ `by_token`); IP —
  резерв, если токена нет. Перезагрузка вкладки и другой браузер на том же телефоне
  остаются тем же устройством.
- **Комната (room)** — серверный объект передачи: кто отправитель, кто получатель,
  состояние (`wait` → `ok` → `done` / `abort`), прогресс, список файлов, имя временной папки.
- **Состояние живёт на сервере.** Страница только отображает его; поэтому процесс видно
  с любой вкладки того же устройства.
- **ПК — тоже устройство** с зарезервированным `id = 0` («Этот компьютер»), но участвует
  браузером: страница на `http://<адрес>` подтверждает и принимает файлы сама,
  окно — только панель (журнал, счётчики, передачи).

Подробности и диаграммы — в `ARCHITECTURE.md`.

## 5. Пользовательский сценарий (как задумано)

1. Пользователь запускает `neonsend.exe`, выбирает папку приёма (запоминается).
2. На телефоне сканирует QR → открывается страница.
3. **Экран 1** — ввод имени устройства (если сервер уже знает это IP — экран пропускается).
4. **Экран 2** — список устройств в сети. Выбор получателя → у получателя всплывает
   «… хочет передать вам файлы. Принять?». Есть кнопка «Переименовать устройство».
5. **Экран 3 (отправитель)** — имя получателя, зона drag&drop, кнопки «Файлы», «Папка»,
   «Отмена», «Назад», полоса прогресса загрузки на сервер.
6. **Экран 4 (получатель)** — имя отправителя, «ожидание отправителя», та же полоса сначала
   показывает загрузку отправителя, затем (после «Загрузить всё») — скачивание всех файлов
   со скоростью и «осталось».
7. «Назад» на экранах 3/4 → confirm → на другом устройстве «отправитель/получатель вышел
   из сессии», передача прерывается.

Файлы между двумя устройствами физически проходят через ПК, но пишутся не в папку приёма,
а в `<папка приёма>/Temp(отправитель-получатель-номер-комнаты)`; сами не удаляются — их
чистит кнопка «Удалить временные папки» в окне (при активной передаче — с подтверждением).
При передаче на ПК файлы попадают прямо в папку приёма.

## 7. Не реализовано / запланировано (D)

1. **P2P-режим телефон↔телефон напрямую (WebRTC)** — обсуждался, отложен. Исследование
   показало: через один Wi-Fi relay через ПК обычно не медленнее, а надёжнее; WebRTC требует
   TURN/сигналинга, ломается на client isolation, iOS засыпает в фоне.
2. **`neon.local` (mDNS)** — был сделан и **удалён** 16.11: на Android не резолвился; короткого
   адреса нет, только `http://<ip>:<port>` и QR.
3. **PIN/токен сессии, HttpOnly-cookie** — не сделано; защита ограничена подтверждением
   на получателе + Host/Origin.
4. **Лимиты одновременных соединений** — не сделано (есть таймаут простоя `upload` 60 с
   и таймаут+повтор на клиенте). Таймауты заголовков/тела не настраивались.
5. **HTTPS** — осознанно отклонено (см. DECISIONS).
6. **Правило брандмауэра** — сделано по программе: `neonsend.exe`, TCP и UDP, любые
   порты, профиль «Публичный», входящие разрешены. Отдельных правил на диапазон не нужно.
7. **Автозапуск с Windows** — не нужен по решению пользователя.
8. **Замер скорости / выбор режима передачи** — обсуждалось, не сделано.
9. **Уведомление второй стороны о смене имени устройства** — не сделано (не требуется явно).
10. **Список файлов на ПК в браузере («обменник»)** — было реализовано и **удалено** по
    просьбе пользователя.

## 9. Известные проблемы (кратко; подробно — `BUGS_AND_ISSUES.md`)

**Остаются:**
- Устройство идентифицируется по IP: смена IP = новое устройство; два устройства за одним
  NAT сливаются. Решается только введением постоянного токена в localStorage.
- Нет HTTPS/токена сессии: любой в той же сети, кто знает адрес, может открыть страницу
  и попросить имя. В домашней сети приемлемо, для офиса — нет.
- Автозагрузка нескольких файлов на iOS: Safari спрашивает подтверждение на каждую загрузку;
  файлы >64 МБ отдаются прямой ссылкой без прогресса.
- Firewall: правило сделано по программе (`neonsend.exe`, TCP+UDP, любые порты), поэтому
  смена порта (80 → 8765 и т. д.) подключение не ломает.
- `.part`-файлы отменённых передач чистятся при отмене/уходе; при аварийном обрыве
  остаются до удаления Temp-папок кнопкой в окне.
- Нет интеграционных тестов HTTP в репозитории (проверки делались ad-hoc скриптами
  в `C:\Temp\opencode`, они не версионируются).
- UI не покрыт автотестами; визуал проверялся скриншотами, на реальных телефонах — не полностью.

**Обойдено/принято как есть:** HTTP вместо HTTPS; идентификация по IP; отсутствие PIN.

## 11. Почему отказались от Python-версии (историческая справка)

Файл `C:\Temp\opencode\transfer.py` (порт 8765, приёмник `C:\Users\user\Downloads\Received`)
работал и принимал десятки тысяч файлов, но имел:
- HTML-список файлов, собранный строкой из имён → потенциальный stored XSS;
- отсутствие проверок Host/Origin;
- отсутствие таймаутов;
- печать имён файлов в лог;
- главное: при закрытии Python передача на странице **не останавливалась**.

Эти уроки перенесены в Rust-версию: `textContent` вместо innerHTML, guard по Host/Origin,
ping с остановкой передачи, журнал без имён файлов.

## 12. Правила работы над проектом (согласовано с пользователем)

1. Перед изменением кода — прочитать актуальные файлы, не полагаться на память/документацию.
2. Не переписывать работающие части без необходимости; минимальный рабочий diff.
3. Архитектурные изменения — только после согласования.
4. Не удалять функционал без согласования.
5. Не добавлять зависимости без объяснения; сначала стандартная библиотека и уже
   подключённые крейты.
6. Не повторять отклонённые решения без новых обстоятельств (см. `DECISIONS.md`).
7. После изменений — собирать и запускать тесты; сообщать, какие файлы изменены.
8. Не заявлять «работает», если не проверено; явно писать, что именно не проверено.
9. Первопричина, а не маскировка симптома.
10. Отвечать по-русски, кратко и по делу; сложные вещи объяснять простыми словами.
11. Пользователь предпочитает: чтобы программа требовала минимум действий, работала без
    установки компонентов и на как можно большем числе версий Windows.
12. Всё хранится локально, без облачных сервисов.

Технические особенности окружения, которые нужно знать:
- PowerShell в этой системе **портит кириллицу** при чтении/записи файлов через пайплайны —
  массовые правки текста делать через `node`-скрипты или инструменты редактирования.
- Перед сборкой нужно завершать `neonsend.exe` (`taskkill /f /im neonsend.exe`), иначе
  ошибка «failed to remove file».
- Вывод cargo в перенаправленном файле приходит в cp1251 с NUL-байтами; надёжнее искать
  строку `Finished`.
- Сборка требует PATH: `%USERPROFILE%\.cargo\bin` и `C:\Users\user\Tools\mingw64\mingw64\bin`.

## 14. Рекомендации нового ИИ (честная оценка)

**Сильные стороны:** компактный, понятный код без фреймворкового оверхеда; состояние
передачи на сервере (переживает перезагрузку вкладки); аккуратная работа с путями и
экранированием; грамотный выбор LAN-IP; портативность.

**Слабые стороны:** нулевая автоматизация фронтенда, отсутствие git и CI, идентификация
устройств по токену без аутентификации (токен можно подделать), отсутствие TLS, отсутствие
лимитов — то есть проект «домашний»,
а не «корпоративный».

**Не делать без явной просьбы:** переписывать страницу на фреймворк, вводить БД,
добавлять аккаунты/облако, ломать формат `Temp(от-кому-комната)` (на префикс `Temp(`
завязаны `delete_temps` и подсчёт размера в окне), менять способ идентификации
устройств (токен в `localStorage`; IP — резерв).
