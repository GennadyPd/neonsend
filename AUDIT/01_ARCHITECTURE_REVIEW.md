# 01. Architecture Review

## Стек (фактический)
- Rust 2021, один бинарник Windows GUI + встроенный HTTP-сервер.
- UI: `eframe/egui 0.28.1` (обновлено с 0.27), `rfd 0.14.1` (диалоги), `qrcode 0.14`, `if-addrs 0.15`, `chrono 0.4`.
- Сервер: `axum 0.7.9` + `tokio 1` (multi-thread, net, fs, io-util, macros, time, sync), `futures-util`, `serde`/`serde_json`.
- Клиент: один статический `page.html` (1383 стр.) с инлайн CSS/JS, SSE + polling.
- Release: `opt-level="s"`, LTO, `codegen-units=1`, `strip=true`; `panic=abort` убран — паника UI ловится и окно перезапускается.

## Компоненты и потоки
```
main() ─ panic hook (crash.log) ─ цикл до 5 рестартов run_native
  └ App::update → draw() под catch_unwind → UI (egui)
boot() → server::start() (std::thread + tokio runtime)
  ├ TcpListener 8765..=8790 (фолбэк), Router 21 маршрут, guard middleware
  ├ Shared { root, log, received, devices, by_ip, by_token, reqs, next, local, names }
  └ sweep каждые 30 с: удаление Done/Abort старше 600 с
Браузер ── GET / (page.html) ── SSE /api/events ── POST /api/* ── /dl
```
Передача файлов: отправитель режет на чанки (8 МБ; iOS — всегда), POST `/api/upload?off&size&last`, сервер пишет `<name>.part` в `Temp(<from>-<to>-<rid>)` и переименовывает при `last=1`; получатель скачивает через `/dl`. Для получателя-PC файл пишется сразу в папку приёма.

## Сильные стороны
- Один exe, нет установки, нет внешних сервисов, всё в LAN.
- Разделение `main.rs` (UI/жизненный цикл) и `server.rs` (HTTP/состояние) понятное; `page.html` самодостаточен.
- Guard Host/Origin, `safe_rel_path` (запрет `..`, control-символов, зарезервированных имён Windows, обрезка хвостовых точек/пробелов) — закрывают основные веб-классы атак.
- Устойчивость UI: сервер поднимается один раз в `boot()`, паника кадра не убивает сервер, окно перезапускается (до 5 раз).
- Прогресс/статусы через SSE + fallback polling; таймауты на ответ (180 с) и на чанк (60 с).

## Слабые места
1. **Идентичность = число `id`** в query. Нет сессии/секрета; все проверки — «пришёл ли этот id». Это архитектурный корень NS-SEC-01/02 и части NS-FUN-*.
2. **Состояние в 8 мьютексах** (`devices`, `by_ip`, `by_token`, `tok_names`, `reqs`, `root`, `log`, `names`), порядок захвата важен (`reqs → devices`), все `.unwrap()` → паника = вечная блокировка.
3. **JSON собирается `format!`** в 10+ местах с ручным `esc()`/`esc_text()` — работает, но хрупко; `serde_json` уже в зависимостях.
4. **Жизненный цикл Temp-папок** неполный: создаются при relay, удаляются только при выходе приложения/кнопкой, не после Done/clear → двойной расход диска.
5. **Прогресс на клиенте считается из `items[].size`**, который для чанковых загрузок неверен (NS-FUN-01).
6. **Документация опережает код**: 22 маршрута vs 21, D-05 «устройство = IP» (уже токен), D-07 `pc_pending` (удалено), D-22 «wakeLock не используется» (используется), «3 теста» vs 5 и т.д.

## Границы и предположения
- Модель угроз в документации: доверенная LAN, HTTP без TLS, устройства-браузеры. Аудит проверял и сценарий «в LAN есть чужое устройство» — там модель не держится.
- Данные комнат только в памяти: рестарт сервера рвёт активные передачи (B-10, заявлено осознанно).
- Windows-only: FFI `GetDiskFreeSpaceExW`, `rundll32`, пути `%APPDATA%`, лимит MAX_PATH.

## Рекомендации по архитектуре (без переписывания)
- Ввести `sid` (случайный 128-битный токен), выдаваемый в hello SSE и cookie; все мутирующие эндпоинты и `/dl|/part|/exists` проверяют `sid → device id`, а не параметр `id`. Объём: ~150–250 строк в `server.rs` + `page.html`.
- Заменить `format!`-JSON на `serde_json::json!` там, где возвращаются структуры (снимет класс ошибок экранирования).
- Хранить `Instant` последнего использования Temp и удалять папку комнаты в `done/clear/abort`.
- Добавить `Content-Type: application/json` и `Cache-Control: no-store` в общий helper ответов.
