# 02. Security Audit

Методика: source-first (скиллы `security-audit`, `reviewing-security`), проверка каждой находки живым запросом к работающему серверу. Правило: находка без пути «ввод атакующего → последствие» не считается уязвимостью. Уровни: CRITICAL/HIGH/MEDIUM/LOW/INFO + уверенность.

## Модель угроз
- Сервер слушает LAN-интерфейс (`192.168.1.25:8765`), доступен любому устройству в подсети.
- Нет TLS, нет логинов. Заявленная защита: Host/Origin guard + одноразовость id.
- Атакующий: любой хост в LAN (гость, IoT, скомпрометированное устройство), умеющий делать HTTP-запросы.

## NS-SEC-01 — CRITICAL — нет аутентификации и авторизации (уверенность: высокая)
Путь: `POST /api/answer?id=4&accept=1` → сервер верит, что это получатель. Кода аутентификации нет: `id` — единственный «креденшл», перебирается (id малы и видны в `/api/state`, `suggest: "label · №id"`).

Доказано живыми запросами с ПК (id=0), в момент реальных сессий устройств 1 и 3:
- `POST /api/request?from=1&to=3&files=1` → создана комната 4 от имени чужих устройств (200, `{"id":4}`).
- `GET /api/state?id=1` → отдал комнату устройства 1, включая `temp:"Temp(PC-1-Phone-4)"`.
- `POST /api/answer?id=4&accept=1` → `{"ok":true}` без идентичности (обход согласия получателя).
- `POST /api/leave?id=999&req=4` → `{"ok":true}` — чужой id прервал передачу.
- `POST /api/done?id=999&req=<room>` → `{"ok":true}` — комната завершена и удалена.
- `POST /api/text?req=<room>&id=0` работает от имени отправителя; от id получателя — `{"error":"передача не разрешена"}` (единственная проверка, и та по параметру).

Последствия: подмена устройств, блокировка чужих передач (busy на 180 с), принудительное принятие/отклонение, завершение, чтение метаданных (имена файлов, размеры, Temp-пути), отправка текста от чужого имени. Это полный обход модели «получатель подтверждает приём».

Рекомендация: сессионный секрет на устройство (`sid` в cookie, выдаётся при SSE-hello), все мутирующие вызовы и `/dl|/part|/exists` проверяют `sid`; параметр `id` оставить только для отладки/PC. Минимум: HMAC/подпись `id` секретом, известным только клиенту.

## NS-SEC-02 — HIGH — IDOR: файлы и метаданные по перебираемым id (уверенность: высокая)
- `/dl` требует `id==from|to`, но `id` перебираем; `PC_ID=0` — константа, известная всегда. `GET /dl?req=<room>&name=<file>&id=0` вернул файл (200, 20 байт) без какой-либо аутентификации.
- `/api/part?req=<room>&name=c.bin&id=999` → `{"off":10}` — размер `.part` любой комнаты при любом id (проверки участника нет).
- `/api/exists?req=<room>` → `{"have":["c.bin"]}` — оракул существования файлов в папке приёма/комнаты без проверки владельца.
- `/api/state?id=N` отдаёт полную комнату устройства N без аутентификации.

Последствия: скачивание файлов идущей relay-передачи (конфиденциальность), разведка имён/размеров, обход «одноразовых» ссылок.

Рекомендация: та же авторизация по `sid`; `/dl` — только участникам комнаты; `part/exists` — только `from` (или `to` для прогресса); `state` — только себе.

## NS-SEC-03 — MEDIUM — DoS и расход ресурсов (уверенность: высокая)
- Создание комнаты от имени чужих устройств занимает их на 180 с («вы уже в передаче»), повторяемо бесконечно.
- Нет лимита соединений/частоты (B-09), `DefaultBodyLimit::disable()` глобально; локальные лимиты есть: push 4 МБ, exists 8 МБ (100 000 имён), text 64 КБ.
- `planned` ограничен 2000, но `items` растёт без ограничения за время комнаты.
- `leave/done/clear` позволяют любому рвать чужие сессии (см. NS-SEC-01).

Рекомендация: лимит одновременных комнат на устройство и на сервер, rate-limit по IP (например, token bucket), `DefaultBodyLimit` с разумным максимумом, лимит `items`.

## NS-SEC-04 — MEDIUM — отравление мьютексов (уверенность: средняя)
Все обращения к `Mutex` — `.unwrap()`. Паника при захваченном мьютексе (например, в `prune`/`push_room` при битом состоянии) делает мьютекс отравленным навсегда: каждый следующий запрос паникует → сервер жив, но все API мертвы до перезапуска. `catch_unwind` стоит только вокруг отрисовки кадра, не вокруг хендлеров.

Рекомендация: `lock().unwrap_or_else(|e| e.into_inner())` в общем helper, либо `parking_lot`.

## NS-SEC-05 — LOW — нет security-заголовков на `/` (уверенность: высокая)
`GET /` не отдаёт CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`. `page.html` можно встроить в iframe на внешнем сайте; guard пропускает, т.к. Host/Origin соответствуют серверу. Кликджекинг: жертва нажимает «Принять» в невидимом iframe. Практическая ценность ограничена (LAN-адрес), но при NS-SEC-01 защита и так нулевая.

Рекомендация: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, минимальный CSP (`default-src 'self' 'unsafe-inline'` из-за инлайн-JS).

## NS-SEC-06 — LOW — API без Content-Type/Cache-Control (уверенность: средняя)
Большинство ответов — `String` без заголовков; `nosniff` есть только у `/dl`. Браузер может сниффать тело; промежуточные кэши теоретически могут кэшировать ответы (в LAN маловероятно). У `/dl` корректные `Content-Type: application/octet-stream`, `Content-Length`, `Content-Disposition` (ascii + `filename*`).

Рекомендация: общий helper ответа с `application/json` + `no-store`.

## NS-SEC-07 — LOW — resume без проверки смещения и без хеша (уверенность: высокая)
`upload` при `off>0` открывает существующий `.part` и делает `seek(off)` без сверки с текущей длиной. Проверено: чанк 10 Б, затем чанк с `off=100` → файл 105 байт с нулевой дырой, в `items` размер 5; скачивание отдало 105 байт. Потеря/дубль чанка на клиенте даёт молчаливо испорченный файл. Хеш не сверяется (задокументированный shortcut в `server.rs` 1364–1365).

Рекомендация: отклонять `off > len(.part)` (409), сверять `off+size == итоговый размер` на `last=1`, опционально sha256 в `planned`/`push`.

## NS-SEC-08 — INFO — guard работает (положительно)
Проверено: `Host: evil.com` → 403 «чужой адрес»; `Origin: http://evil.com` → 403 «чужой источник»; запрос без комнаты/неизвестный маршрут → 403/404. DNS-rebinding в базовом виде закрыт (Host должен совпасть с `ip:port`). Обратная сторона: доступ по имени компьютера (`http://hostname:8765`) ломает все API — функциональное ограничение (NS-PORT-01).

## NS-SEC-09 — INFO — транспорт и токен (принято осознанно)
HTTP без TLS; токен устройства в `localStorage['neon-token']` (B-02). В доверенной LAN риск умеренный; в общей сети — перехват/подмена. Не является новой находкой, зафиксировано для полноты.

## Проверено и не подтверждено
- **XSS**: в `page.html` весь пользовательский текст вставляется через `textContent`; единственное вхождение `innerHTML` — комментарий (стр. 582). Сервер экранирует JSON (`esc`, `esc_text`) и режет управляющие символы в метках. Не подтверждено.
- **Path traversal**: `safe_rel_path` отклоняет `..`, абсолютные имена, control-символы; проверено `../../etc` → 400. Обход не найден. Симлинки не проверяются (на Windows для непривилегированного процесса малоприменимо).
- **SQL/шаблоны/команды**: не используются; `unsafe` только `GetDiskFreeSpaceExW`.
- **CSRF**: CORS-заголовков нет, но guard требует совпадения Origin/Referer; простые GET `/dl` и `/api/*` всё равно без auth (см. NS-SEC-01/02) — CSRF неприменим как отдельный класс.
- **Утечка секретов в логи**: crash.log содержит бэктрейс, без токенов; devices.json — метки/IP, без секретов.

## Итог
Единственная принципиальная проблема — отсутствие аутентификации/авторизации; она превращает все остальные мелкие послабления в эксплуатируемые. При закрытии NS-SEC-01/02 приложение становится адекватно безопасным для доверенной LAN.
