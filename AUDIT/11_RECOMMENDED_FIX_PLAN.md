# 11. Recommended Fix Plan

План упорядочен по риску и цене. Оценки трудозатрат — для одного разработчика, без учёта ревью. Ничего не реализовано в рамках аудита (запрет на правку кода).

## P0 — до любого использования в недоверенной сети
### 1. Аутентификация устройства и авторизация запросов (SEC-01, SEC-02)
- Ввести `sid`: случайные 128 бит при первом SSE-подключении, выдавать через `Set-Cookie` (HttpOnly, SameSite=Lax) и/или в hello.
- Сервер: `sid → id`; все мутирующие вызовы (`request/answer/leave/done/clear/text/push/upload/progress/sender_done/abort`) берут id из сессии, параметр `id` игнорируют/проверяют на совпадение.
- `/dl` — только участникам комнаты; `/api/part`, `/api/exists` — только отправителю комнаты (и получателю для part, если нужно).
- `/api/state` — отдавать только свою комнату.
- Клиент: хранить cookie автоматически; убрать `?id=` из URL (оставить для отладки за флагом).
- Объём: ~200–250 строк `server.rs` + ~30 строк `page.html`.
- Приёмка: запрос с чужим/отсутствующим `sid` → 403 на всех перечисленных; живой цикл 0↔1 работает; unit-тесты на 5 отказов.

## P1 — устойчивость и корректность (1–2 дня)
### 2. Лимиты и защита от DoS (SEC-03)
- `DefaultBodyLimit` с максимумом (например, 32 МБ на чанк) вместо глобального disable.
- Лимит одновременных комнат (1 на устройство уже есть; добавить глобальный, например 32) и простой rate-limit по IP (token bucket 20 req/s).
- Лимит `items` (например, 5000) с ошибкой.

### 3. Мьютексы без паники (SEC-04)
- Helper `fn lock<T>(m:&Mutex<T>)->MutexGuard<T>{ m.lock().unwrap_or_else(|e| e.into_inner()) }` и заменить все `lock().unwrap()`.

### 4. Удаление Temp после завершения (FUN-05, FUN-06)
- В `done`/`clear`/`abort` удалять папку комнаты, если нет активной записи (флаг «пишется»).
- При старте чистить `.part` старше N часов в папке приёма (с подтверждением/логом).

### 5. Корректный размер в комнате (FUN-01)
- Хранить суммарный `written` по имени (или считать `bytes_done` из фактических записей) и отдавать его в `items`.
- Проверить: файл 20 Б двумя чанками → `size:20`; 105 Б → `105`.

### 6. Resume-валидация (SEC-07)
- `off > len(.part)` → 409 (как сейчас для отсутствующего `.part`).
- На `last=1` сверять `off+size` с ожидаемым размером из `planned` (если есть) и логировать расхождение.

### 7. Security-заголовки (SEC-05, SEC-06)
- `/`: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, CSP `default-src 'self' 'unsafe-inline'`.
- Общий helper для JSON-ответов: `application/json; charset=utf-8`, `Cache-Control: no-store`.

## P2 — UX, доступность, надёжность (2–3 дня)
### 8. A11y-минимум (UX-01…UX-06)
- `<h1 class="sr-only">`, `<label for="nameInput">`, `main/header`.
- `--faint` ≥ 4.5:1 во всех темах; light `--neon` темнее.
- Модалки: `id` + `aria-labelledby`, focus-trap, возврат фокуса.
- Прогресс: `role="progressbar"` + `aria-valuenow`, статус `aria-live="polite"`.
- Чип темы 44 px; стрелки в списке; замена `confirm()`.

### 9. Состояние и SSE (FUN-03, FUN-04)
- Переподключение SSE на `visibilitychange`/`online`; сброс комнаты при `room == null`.

### 10. Крупные файлы (FUN-02)
- Прогресс для прямой ссылки: либо стриминг с `fetch`+`ReadableStream` в File System Access (запрещено для iOS) — проще: `Range`-докачка и прогресс по `Content-Length` в обычном `<a download>` не выйдет; альтернатива — поднять порог и оставить как есть, но показать честный текст «скачивание браузером, прогресс недоступен».
- Минимальный шаг: явное сообщение вместо молчаливого отсутствия прогресса.

### 11. Единый контракт ошибок (BE-03)
- 4xx + JSON на всех эндпоинтах; клиент — один обработчик.

### 12. Темп-имена и пути (BE-04)
- `Temp-<rid>` вместо меток; миграция старых папок при старте.

## P3 — гигиена (по возможности)
13. `git init` + коммит (BE-06).
14. Тесты: `safe_rel_path` (8 кейсов), авторизация (5), чанки/resume (2), лимиты (3) — TST-01.
15. Синхронизация документации по списку DOC-01.
16. `cargo-audit` в релизный чек-лист (DEP-01).
17. Single-instance + явный порт (FUN-07/PORT-02).

## Порядок и зависимости
P0 → P1.1–P1.3 (защита) → P1.4–P1.6 (данные) → P1.7/P2.8 (заголовки/a11y) → P2.9–P2.12 → P3.
Пункты 1–6 меняют поведение API — после них обязателен прогон живого цикла и 5 unit-тестов; пункты 8, 13–16 не трогают протокол.

## Статус выполнения (16.11.2026)

P0 (аутентификация/авторизация всех мутирующих вызовов и `/dl|/part|/exists`), P1 (security-заголовки, лимит комнат, `lock()`, сверка `off`, размер чанков) и P2-a11y выполнены. Проверки — `14_POST_FIX_VERIFICATION.md`. Не выполнены: git и синхронизация документации, FUN-02/05…09, BE-*, тесты клиента.

## Что НЕ делать
- Не менять архитектуру (комнаты в памяти, HTTP без TLS, `Temp(...)`-схему) — вне рамок и без запроса.
- Не обновлять eframe ради F-50 без отдельной задачи.
- Не добавлять зависимости для тестов/лимитов — стандартной библиотеки и serde достаточно (кроме опционального `parking_lot`, если решите).
