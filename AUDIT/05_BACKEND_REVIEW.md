# 05. Backend Review

## Обзор
`src/server.rs` (1951 стр.) — axum-роутер, SSE, состояние в памяти, файловый relay. `src/main.rs` (1167 стр.) — egui-окно, конфиг, жизненный цикл, QR, свободное место.

## Состояние и конкурентность
- `Shared` держит 8 мьютексов: `devices`, `by_ip`, `by_token`, `tok_names`, `reqs`, `root`, `log`, `received` (+ `names`, `local`, `next`). Порядок захвата важен (`reqs → devices`), документирован в коде, но не enforced.
- Все блокировки — `.unwrap()`; отравление мьютекса = отказ всех эндпоинтов (NS-SEC-04).
- `prune()` вызывается не во всех хендлерах: часть путей видит «мёртвые» устройства до следующего prune; sweep-таск чистит только Done/Abort старше 600 с.
- `spawn`-таймеры (180 с на ответ, 60 с на чанк) не отменяются при `clear/done` — срабатывают вхолостую, держат `Arc<Shared>` (утечки нет, но лишние задачи).

## Контракты API
- Единого формата ошибок нет: часть хендлеров возвращает `200 {"error":"..."}` (`request`, `answer`, `leave`, `done`), часть — 4xx (`upload` 409/403, `part` 400, `dl` 403/404). Клиент вынужден разбирать оба варианта (в `page.html` так и сделано).
- Большинство ответов — `String` без `Content-Type`; заголовки есть только у `/` и `/dl`.
- Параметры — в query, тела — сырые/JSON, лимиты локальные (`push` 4 МБ, `exists` 8 МБ, `text` 64 КБ), глобальный `DefaultBodyLimit::disable()`.

## Работа с файлами
- `safe_rel_path`: отклоняет пустые/`..`/абсолютные компоненты, >1000 байт, control-символы, `: * ? " < > |`, хвостовые точки/пробелы, зарезервированные DOS-имена. Аккуратная реализация, покрыта только косвенно (живые тесты).
- `upload`: `.part` + rename, `sync_all`, таймаут чанка; при `off>0` seek без проверки длины (NS-SEC-07); `items` пишет только последний чанк (NS-FUN-01).
- `free_name` для `ow=2`; `ow=0` — пропуск (`skip:true`).
- `download`: `Content-Disposition` с ascii-фолбэком и `filename*` (RFC 5987), `nosniff`, `Content-Length`.
- `delete_temps` при выходе приложения; после завершения комнаты Temp не удаляется (NS-FUN-05).

## SSE и клиенты
- Канал `broadcast` ёмкостью 64, `Lagged` пропускается; hello содержит `id`, `named`, `suggest`.
- Устройство ищется по токену → IP → новый id; `PC_ID=0` для локального IP.
- Пинг каждые 2 с, `/api/state` каждые 3 с как fallback (дублирование данных).

## UI/жизненный цикл (main.rs)
- Сервер стартует один раз в `boot()`; UI-падение ловится `catch_unwind` вокруг `draw`, окно перезапускается до 5 раз с паузой 500 мс.
- Panic hook пишет `%APPDATA%\NeonSend\crash.log` с бэктрейсом.
- Защита от закрытия при активной передаче; кнопка очистки Temp с подтверждением.
- `config.json {root,theme}`; папка по умолчанию `%USERPROFILE%\Downloads\NeonSendTemp`.
- `local_ip()` ранжирует приватные диапазоны и отбрасывает виртуальные адаптеры; при нескольких активных интерфейсах возможен неверный выбор (не проверяли).

## Находки
- **NS-BE-01 (MEDIUM)**: ручная сборка JSON через `format!` + самописные `esc/esc_text` в 10+ местах; риск ошибки экранирования при доработках. `serde_json` уже подключён.
- **NS-BE-02 (LOW)**: неполный `prune`, неотменяемые таймеры, отсутствие единого слоя ответов.
- **NS-BE-03 (LOW)**: непоследовательные коды ошибок (200 vs 4xx).
- **NS-BE-04 (LOW)**: имя Temp-папки из меток устройств (`Temp(PC-1-Phone-5)`): переименование устройства меняет путь, возможны длинные пути (MAX_PATH) и коллизии; `rid` спасает от совпадений.
- **NS-BE-05 (INFO)**: известный баг egui `hit_test` (F-47/F-50) — паника возможна после отрисовки, вне `catch_unwind`; исправлен в egui 0.37, обновление отложено осознанно. Риск mitigated перезапуском окна, но сервер и передачи при рестарте окна не рвутся (сервер в `boot()`).
- **NS-BE-06 (INFO)**: нет git/бэкапа (R-01), документация расходится с кодом (NS-DOC-01).

## Качество кода
Плюсы: имена понятные, функции короткие, комментарии по делу, никакой лишней абстракции, `unsafe` изолирован (FFI). Минусы: дублирование JSON-шаблонов, «магические» таймауты (9 с, 180 с, 600 с, 60 с) разбросаны, нет структур запроса/ответа на сервере (`serde` используется точечно).

Оценка backend/кода: **6/10** — работает надёжно в штатном сценарии, но хрупко к изменениям.
