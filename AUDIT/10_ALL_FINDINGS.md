## SEC-01 — Нет аутентификации и авторизации
- **Критичность:** CRITICAL (уверенность В) · **Категория:** Security / AuthN+AuthZ
- **Путь:** `src/server.rs` — `request`, `answer`, `leave`, `done`, `clear`, `text`, `send_text`, `progress`
- **Доказательство:** `POST /api/request?from=1&to=3&files=1` → комната от имени чужих устройств; `POST /api/answer?id=4&accept=1` → `{"ok":true}` без идентичности; `POST /api/leave?id=999&req=4` → `{"ok":true}`; `POST /api/done?id=999&req=5` → `{"ok":true}`.
- **Описание:** личность клиента — целое `id` из query; отдельного секрета/сессии нет. Проверки «этот id участвует в комнате» местами есть (upload/progress/abort), но сам id подделывается.
- **Сценарий:** любой хост в LAN узнаёт id из `/api/state`/`suggest`, создаёт комнату от имени жертвы, принимает/отклоняет/прерывает/завершает передачи, шлёт текст.
- **Последствия:** полный обход согласия получателя, подмена устройств, срыв передач, утечка метаданных.
- **Рекомендация:** секрет на устройство (`sid`, cookie из SSE-hello), проверять его на всех мутирующих вызовах; `id` — только отображение.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## SEC-02 — IDOR: файлы и метаданные по перебираемым id
- **Критичность:** HIGH (В) · **Категория:** Security / Access control
- **Путь:** `download` (`/dl`), `part_size` (`/api/part`), `exists` (`/api/exists`)
- **Доказательство:** `GET /dl?req=<room>&name=c.bin&id=0` → 200, тело файла (20 б); `GET /api/part?req=<room>&name=c.bin&id=999` → `{"off":10}`; `POST /api/exists?req=<room>` → `{"have":["c.bin"]}`; `GET /api/state?id=<N>` отдаёт чужую комнату.
- **Описание:** `/dl` пускает при `id==from|to`, `PC_ID` всегда 0; `part`/`exists` не проверяют участника вовсе. id малы и перебираемы.
- **Сценарий:** атакующий перебирает id комнат и скачивает файлы идущих передач, узнаёт имена/размеры, готовит целевые атаки.
- **Последствия:** конфиденциальность (файлы), разведка структуры папки приёма.
- **Рекомендация:** авторизация по `sid`; `/dl` — только участникам; `part/exists` — только отправителю; `state` — только себе.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## SEC-03 — DoS: блокировка устройств, отсутствие лимитов
- **Критичность:** MEDIUM (В) · **Категория:** Security / Availability
- **Путь:** `request` (busy + таймер 180 с), `start` (`DefaultBodyLimit::disable()`), `push`, `exists`
- **Доказательство:** повторный `request` → «вы уже в передаче»; после чужого запроса устройство занято до 180 с; лимитов соединений/частоты в коде нет.
- **Описание:** комната блокирует оба устройства; создать её может кто угодно (SEC-01); глобальный лимит тела отключён, локальные — 4/8 МБ/64 КБ; `items` не ограничен.
- **Сценарий:** цикл чужих `request` держит устройства «занятыми»; параллельные большие тела расходуют диск/память.
- **Последствия:** отказ в обслуживании, раздувание памяти/диска.
- **Рекомендация:** лимит комнат на устройство/IP, rate-limit, `DefaultBodyLimit`, лимит `items`.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## SEC-04 — Отравление мьютексов
- **Критичность:** MEDIUM (С) · **Категория:** Security / Reliability
- **Путь:** все `lock().unwrap()` в `server.rs`
- **Доказательство:** статический анализ; при панике в хендлере мьютекс остаётся отравленным, каждый следующий `lock().unwrap()` паникует.
- **Описание:** `catch_unwind` есть только вокруг отрисовки кадра, не вокруг хендлеров.
- **Сценарий:** одна паника при захваченном мьютексе (например, в `prune`/`push_room`) → все API отвечают 500/рвут соединение до перезапуска приложения.
- **Последствия:** постоянный отказ сервера при живом окне.
- **Рекомендация:** `lock().unwrap_or_else(|e| e.into_inner())` в helper или `parking_lot`.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## SEC-05 — Нет security-заголовков на `/`
- **Критичность:** LOW (В) · **Категория:** Security / Web hardening
- **Путь:** `index()` — только `Content-Type` и `Cache-Control`
- **Доказательство:** `GET /` без CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy.
- **Описание:** страницу можно встроить в iframe с внешнего сайта; guard пропускает запросы (Host/Origin совпадают).
- **Сценарий:** кликджекинг кнопки «Принять» на LAN-странице.
- **Последствия:** UI-redressing; в связке с SEC-01 ценность защиты и так нулевая.
- **Рекомендация:** `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, минимальный CSP.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## SEC-07 — Resume без проверки смещения, без хеша
- **Критичность:** LOW (В) · **Категория:** Security/Data integrity
- **Путь:** `upload` (ветка `off>0`), shortcut-комментарий 1364–1365
- **Доказательство:** чанк 10 Б, затем `off=100` → файл 105 Б (нулевая дыра), `items`=5, `/dl` отдал 105 Б.
- **Описание:** `seek(off)` без сверки с длиной `.part`; хеш не проверяется.
- **Сценарий:** потеря/дубль чанка или баг клиента → молча испорченный файл, который выглядит целым.
- **Последствия:** порча данных без сигнала пользователю.
- **Рекомендация:** отклонять `off > len(.part)`, сверять итоговый размер, опционально sha256.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## FUN-01 — Неверный размер файла при чанковой загрузке
- **Критичность:** MEDIUM (В) · **Категория:** Functional
- **Путь:** `upload` (запись `items`), `page.html` (прогресс, порог 64 МБ)
- **Доказательство:** файл 20 Б двумя чанками → `items:[{"name":"c.bin","size":10}]`; файл 105 Б → `size:5`.
- **Описание:** в комнату пишется размер последнего запроса, а не суммарный.
- **Сценарий:** iOS (>8 МБ всегда чанками) и любые большие файлы: прогресс и итоговый размер врут, порог «прямой ссылки» срабатывает неверно.
- **Последствия:** неверный UX, ошибки в оценке объёма, путаница при дубликатах.
- **Рекомендация:** хранить суммарный `written` по имени или пересчитывать из `files/bytes_done`.
- **Статус:** исправлено (проверка — `14_POST_FIX_VERIFICATION.md`).

## FUN-02 — Файлы >64 МБ без прогресса и докачки
- **Критичность:** MEDIUM (В) · **Категория:** Functional
- **Путь:** `page.html` (порог 64 МБ, прямая ссылка)
- **Доказательство:** код; B-04.
- **Описание:** крупные файлы отдаются ссылкой на `/dl`, прогресс не считается.
- **Сценарий:** передача видео >64 МБ: пользователь не видит прогресса, при обрыве начинает заново.
- **Последствия:** плохой UX на самом частом крупном сценарии.
- **Рекомендация:** потоковое скачивание с прогрессом или Range-докачка.
- **Статус:** частично исправлено (16.11): байтовый прогресс по-прежнему недоступен браузеру, но UI больше не показывает ложные 100% — пишет «качает браузер: N бол. файл(ов)» и строку в журнале. Проверено живой передачей 65 МБ на телефон. Полное решение (Range + поток) — отдельная задача.

## PORT-06 — Сервер не слушает 127.0.0.1/localhost
- **Критичность:** INFO (В) · **Категория:** Portability / Network
- **Путь:** `src/main.rs` — `boot()` (`TcpListener::bind((ip, port))` с LAN-адресом)
- **Доказательство:** `http://192.168.1.25:8765/api/ping?id=0` → `ok`; `http://127.0.0.1:8765/...` → connection refused; `http://localhost:8765/...` → таймаут. При этом `guard` разрешает Host `localhost`/`127.0.0.1`.
- **Описание:** сокет биндится только на выбранный LAN-адрес; loopback не слушается. Guard-исключения для loopback недостижимы.
- **Последствия:** локальные ярлыки/скрипты и отладка через localhost не работают (на пользователя не влияет — QR и окно ведут на LAN-адрес).
- **Рекомендация:** не требуется; при желании — второй bind на loopback или убрать loopback из guard.
- **Статус:** исправлено (16.11): сервер слушает `0.0.0.0`, `127.0.0.1` и `localhost` отвечают; loopback считается «этим компьютером». Guard проверяет порт и локальный IP, hostname по-прежнему отклоняется.
